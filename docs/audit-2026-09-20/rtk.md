# RTK integration audit — 2026-09-20

Read-only investigation; implementation remains paused. No routing, packages, hooks, launchers, or service settings were changed. Only this report was created. Commands used for diagnostics were version/help/gain reads; useful searches by the parent task naturally produced new RTK records. Counts below distinguish the pre-audit baseline.

## Findings

1. **RTK is currently executable and recording; it is not a background service.** PowerShell resolves `bin/rtk.exe` first, then the compatibility `bin/rtk.cmd`. The native launcher starts `tools/rtk.exe`, sets the bundled database path, and waits for that command. Installed version is **0.49.0**. Useful searches during this audit increased the main database from **419 to 421 commands**, with matching dashboard totals. This verifies the present execution and recording path, not historical uptime. Sources: [launcher](../../native/RtkLauncher.cs#L261), [compatibility shim](../../bin/rtk.cmd), live `--version`, read-only SQLite snapshots, dashboard `/api/stats`.

2. **The apparent stall has a real usage gap, but there is insufficient evidence of a crash.** The last pre-audit recorded command was **2026-09-16 04:23:17 UTC** (11:23 Bangkok). September 16 had five commands and one estimated token saved. No records exist for September 17–19. Running the tray/dashboard alone does not cause raw commands to use RTK; Codex must actually invoke RTK. We did not inspect private conversation contents, so cannot establish whether those dates contained eligible work that should have used RTK. Source: `data/rtk/history.db`, read-only aggregate queries.

3. **Dashboard green/“active” currently means a readable historical database, not recent use or verified command integration.** `collect_rtk()` returns `active=True` after a successful SQL read. The collector then sets health to `ok` based on the current successful read. It does not compare the newest command timestamp with now. A stale counter can therefore remain green indefinitely. There is a separate browser feed-staleness watchdog, but that only detects disconnected/frozen dashboard updates. Sources: [collector](../../dashboard/app.py#L163), [active flag](../../dashboard/app.py#L218), [health derivation](../../dashboard/app.py#L985), [feed watchdog](../../dashboard/app.py#L2180).

4. **Automatic command coverage is narrow and the optional hook is a Headroom hook, not an RTK rewrite hook.** The hook changes eligible commands to `headroom-run.exe -- <original executable> ...`; it does not turn a native `git`/`rg` invocation into `rtk git`/`rtk rg`. It requires a simple explicit absolute Windows `.exe` invocation with `&`, rejects dynamic arguments and consuming pipelines, and preserves unsupported commands. Among the **last 3,000 pre-audit hook checks** (September 14 05:40–September 16 04:23 UTC), **all were skipped**: 1,918 complex syntax, 1,016 ambiguous shell/path, 57 dynamic input, five parse errors, four unsupported commands. The last recorded rewrite was September 13 16:42 UTC. These counts describe the hook's observed checks; they are not an inventory of all Codex tool calls. Sources: [hook](../../Headroom-PreToolUse.ps1#L54), especially the replacement construction around line 108, `headroom/desktop-state/hook-events.jsonl` sanitized aggregates.

5. **The cumulative savings percentage is dominated by one outlier.** Pre-audit totals were 4,823,419 estimated input tokens, 238,331 output tokens, 4,585,140 saved, or **95.06%** across 419 commands. One September 13 `rg` event alone reported 4,475,543 saved tokens—**97.61% of all claimed savings**. Excluding that one event gives **32.18%** output reduction across the other 418 commands. September 14–16 totals were 38,776 saved / 120,899 input, or **32.07%**. The outlier may be a legitimate very large search output; this audit does not establish its underlying content or usefulness. It should not drive the user's expectation for typical tasks. RTK estimates output tokens using bytes/4, not a tokenizer, subscription quota, or billed request usage. Sources: bundled SQLite aggregate queries; [official v0.49.0 README](https://github.com/rtk-ai/rtk/blob/v0.49.0/README.md#L61). Dashboard currently says “characters / 4”, which should be aligned with upstream's byte-based terminology.

6. **The “No hook installed — run rtk init -g” warning is not evidence that Codex integration failed.** In the installed version's upstream source, that warning inspects Claude's directory, settings, and legacy hook. The custom bundle has RTK instructions in the user's Codex AGENTS.md; no RTK.md exists. Upstream documents Codex integration as instructions, whereas Claude integration uses a hook. Installing the warned Claude hook would not repair Codex coverage. Sources: [upstream hook check](https://github.com/rtk-ai/rtk/blob/v0.49.0/src/hooks/hook_check.rs#L26), [warning](https://github.com/rtk-ai/rtk/blob/v0.49.0/src/hooks/hook_check.rs#L95), [integration table](https://github.com/rtk-ai/rtk/blob/v0.49.0/README.md#L414).

7. **No recent parser failures support a current RTK failure.** The main database has 62 parse-failure rows, all September 9 or 12, with 59 marked recovered. There are zero upstream `hook_decisions` rows; that table is not proof that the bundle's separate Headroom hook is absent. An older default database under `AppData/Local/rtk/history.db` contains only 161 historical rows and stopped changing September 13. The inspected launcher and dashboard both use `CodexTokenSaver/data/rtk/history.db`, so no present path mismatch was found. Sources: read-only SQLite aggregates; [launcher database setting](../../native/RtkLauncher.cs#L284), dashboard `.env` allowlisted path fields.

8. **There is no RTK off switch in the current launcher.** It always executes RTK. `HEADROOM_EXACT=1` skips only the secondary Headroom filtering; it does **not** restore original unfiltered native output from RTK. The secondary filter runs only on a conservative command/flag allowlist, only inside Codex, only for redirected stdout, and only on successful bounded outputs. Thus RTK and local Headroom are separate stages requiring separate controls. Sources: [eligibility](../../native/RtkLauncher.cs#L90), [execution](../../native/RtkLauncher.cs#L261), [compression thresholds](../../command_compression.py#L19).

## Smallest safe changes when development resumes

- Replace the RTK green state with separate **Enabled / Last used / Records readable / Error** facts. Show timestamp and time-window totals; keep lifetime totals secondary and visibly estimated. An idle period is not automatically an error.
- Add a persisted **RTK compression** control and a separate **Headroom local output** control. The request proxy is another independent control. Read the selected state when each command begins, so existing tasks can honor it without changing model/reasoning settings. Report when an existing connection needs a restart for another component's setting.
- Measure coverage using safe command-family and outcome metadata; record bypass reasons without raw command arguments. Do not broaden arbitrary shell rewriting simply to make savings rise. Native PowerShell, scripts, pipelines, machine output, and exact-evidence operations must remain reliable.
- For future RTK off behavior, upstream **`rtk proxy <original executable> <arguments>`** is an unfiltered execution mode with usage tracking. It is not a generic “disable all RTK semantics” flag. `rtk read`, `summary`, `err`, and other RTK-only verbs cannot be safely disabled by dropping `rtk` or blindly inserting `proxy`. Stop automatic RTK rewrites when off; for explicit calls use validated mappings for supported native command families, and report unsupported RTK-only operations clearly. Retain safe diagnostics such as version/gain. Preserve argv, stdin, stdout, stderr and exit code. Source: installed `proxy --help`; [upstream CLI definition](https://github.com/rtk-ai/rtk/blob/v0.49.0/src/main.rs#L686), [implementation](https://github.com/rtk-ai/rtk/blob/v0.49.0/src/main.rs#L2859).
- Validate with a few representative fixtures: search with critical late matches, failing tests, exact machine output, non-ASCII output, and commands using quoting/pipelines. Check that disabling either stage truly preserves the relevant originals and that failures/retrieval details remain available. Compare actual delivered output and latency, not just a larger savings counter. RTK filtering and Headroom compression can discard information, so “no quality degradation” requires task-quality evaluation rather than assuming token reduction is always beneficial.

## Limits

No runtime changes or new implementation were made. We did not run workload benchmarks, read private task contents, or infer billing savings from output estimates. Current functionality was evidenced by useful ongoing audit searches; the historical gap may reflect nonuse, unsupported command shapes, changed task behavior, or an intermittent fault not present now. The app currently lacks enough invocation telemetry to disambiguate these causes conclusively.
